# eda-ml

Решение задания «EDA и машинное обучение» вступительного испытания в магистратуру ИТМО «Искусственный интеллект» (AI
Talent Hub).

Репозиторий содержит разведочный анализ данных, выводы по данным и baseline-модель по датасету, выдаваемому на экзамене.

> **Статус.** Ответы на задание отправлялись через платформу AI Talent Hub. В отведённое время часть C не была
> завершена; она доделана после испытания и опубликована здесь как дополнение к сданной работе:
>
> - [`notebooks/solution.ipynb`](notebooks/solution.ipynb) — решение C1–C5 с кодом, расчётами и сохранёнными
>   выводами (авторитетный источник всех чисел);
> - [`results/C_ANSWERS.md`](results/C_ANSWERS.md) — краткая сводка ответов C1–C5;
> - [`results/submission.csv`](results/submission.csv) — файл предсказаний для C1.

## Задача

Бинарная классификация `relief_granted` — предсказать, закончится ли обращение потребителя компенсацией (денежной или
неденежной), чтобы приоритизировать эскалацию. `complaints_test.csv` — последние месяцы наблюдений, то есть будущее
относительно train, поэтому валидация везде out-of-time.

## Решение и результаты

Данные (`complaints_train.csv` ~7.7 ГБ) обрабатываются out-of-core через **DuckDB**; в pandas/scikit-learn попадают
только уже сокращённые таблицы признаков. Модель — `HistGradientBoostingClassifier` с нативной поддержкой категорий,
out-of-fold target encoding для `Company` и частотным кодированием.

Фактически измеренные метрики на отложенном по времени окне валидации (`2024-12-01 … 2025-04-28`, 1 619 082 обращения,
базовая доля позитивов 0.2621):

| метрика                        | значение               |
|--------------------------------|------------------------|
| PR-AUC (average precision)     | 0.4563                 |
| ROC-AUC                        | 0.7612                 |
| скользящая валидация, 4 месяца | PR-AUC 0.5072 ± 0.0749 |

Разбор важности признаков, калибровки, порога эскалации, вклада текста жалобы и схлопывания шаблонных обращений в
инциденты — в [`results/C_ANSWERS.md`](results/C_ANSWERS.md) и в ноутбуке.

## Как проверить решение

Ниже — маршрут для проверяющего, от самого быстрого способа к самому полному.

**1. Прочитать ответы — 5 минут, ничего запускать не нужно.**
[`results/C_ANSWERS.md`](results/C_ANSWERS.md) — сводка по C1–C5: метрики, порог эскалации, вклад текста, оценка числа
инцидентов, ограничения метода. Каждое число там взято из сохранённого вывода ноутбука.

**2. Посмотреть код и доказательства — 15 минут, ничего запускать не нужно.**
[`notebooks/solution.ipynb`](notebooks/solution.ipynb) открывается прямо на GitHub **вместе с сохранёнными выводами** —
таблицами, метриками и графиками. Это авторитетный источник: если сводка и ноутбук расходятся, верен ноутбук. Структура:
секция `Setup`, затем `## C1` … `## C5`. В каждой секции сначала идёт формулировка вопроса, затем код, затем его
фактический вывод, затем ответ и вывод на русском.

**3. Проверить `submission.csv` — 1 минута.** Файл лежит в репозитории, датасет для этого не нужен:

```powershell
uv run python -c "import pandas as pd; s = pd.read_csv('results/submission.csv'); print(s.shape, s.relief_proba.describe())"
```

Ожидаемо: 1 205 944 строки, колонки `complaint_id,relief_proba`, значения — вероятности в (0, 1), а не бинарные метки
(min 0.000051, max 0.997458, mean 0.408367, 80 668 различных значений), пропусков нет. Состав и порядок
`complaint_id` совпадают с `sample_submission.csv` (проверено сравнением массивов).

**4. Полностью воспроизвести расчёты — ~2 часа, нужен датасет.** См. [Данные](#данные) и
[Воспроизведение](#воспроизведение) ниже.

### Что стоит проверить в первую очередь

Если задача — оценить корректность, а не просто увидеть метрику, самое содержательное в решении:

- **исключение полей-утечек** (секция C1): `internal_priority_score`, `company_public_response`,
  `timely_response` заполняются уже **после** разбора обращения. Они исключены не по названию, а по измеренным числам —
  например, `internal_priority_score < 40` даёт 3.4% компенсаций против 92.7% при `>= 60`;
- **валидация out-of-time, а не случайная** (секция C2): доля компенсаций падает с 0.399 на обучающем окне до 0.262 на
  валидационном, поэтому случайное разбиение завысило бы оценку;
- **честно показанная плохая калибровка** (секция C2): ECE 0.1289, средняя предсказанная вероятность 0.3896 против
  фактической 0.2621 — модель годится для ранжирования, но не для абсолютных вероятностей;
- **самокритика валидации** (секция C5): шаблонные массовые обращения пересекают временную границу, и при оценке на
  уровне инцидентов PR-AUC падает — то есть собственная оценка из C2/C4 названа оптимистичной.

## Воспроизведение

```powershell
uv sync                 # создать .venv строго по uv.lock
uv run jupyter lab      # запустить ноутбуки интерактивно
uv run ruff check .     # линтер

# полный неинтерактивный прогон решения (перезаписывает выводы в ноутбуке)
uv run jupyter nbconvert --execute --inplace notebooks/solution.ipynb
```

Полный прогон с нуля занимает около 2 часов, из которых ~75 минут — однократное построение кэшей признаков из CSV
(`cache/*.parquet`, не хранится в git). Повторные запуски переиспользуют кэш (~45 минут). Обучающий CSV читается строго
однопоточно (`parallel=false`): внутри значений `Consumer.Complaint.Narrative` встречаются переводы строки, на которых
параллельный CSV-ридер DuckDB завершается ошибкой.

Модель немного нестабильна между прогонами: `HistGradientBoostingClassifier` в многопоточном режиме даёт неидентичные
результаты даже при фиксированном `random_state=42` (порядок суммирования с плавающей точкой). Ранжирование сохраняется
(Spearman 0.998 между двумя прогонами), но отдельные вероятности могут отличаться, поэтому побитового совпадения
`submission.csv` при перезапуске ожидать не следует.

Все числа в ноутбуке получены одним успешным прогоном (38 из 38 кодовых ячеек, без ошибок). После него в ноутбук
вносились правки, не затрагивающие вычисления: подстановка полученных чисел в текстовые выводы, определение корня
репозитория через поиск `uv.lock`, путь сохранения `submission.csv` в `results/` и косметические правки по `ruff`. Эти
правки не перезапускались, поэтому в сохранённом выводе ячейки C1 путь файла отображается как корень репозитория, хотя
код уже пишет в `results/`.
